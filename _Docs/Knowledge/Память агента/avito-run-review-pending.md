Live Avito GeeTest slide solver, unsolved until 2026-11-02 evening. Run 46 passed 1 of 3 puzzles; runs 47 and 49 (with the new per-attempt diagnostics) logged «довели с ошибкой 4.0 / 4.1 / 4.2 / 4.0 / 3.9 / 4.0 px» — every attempt ended exactly ~4 px past the cutout, so the gap finder was never the main problem. Cause: the puzzle piece follows the slider handle with a lag, the solver measured the lagging position, corrected from it and overshot. Fixed in e6bb6e3: `human.Mouse._settled` now needs two agreeing readings before it trusts a position and uses real time (`_idle`, not scaled by `TIME_SCALE`), and the drag is a fling to ~85% plus two or three short corrective moves, ~1 s in all — the shape the user says works for them by hand.

**Why:** nothing of this is verified on the live site yet; the log line is the evidence.

**How to apply:** after the user's next run, read the newest `RealtyWatch_Win/logs/runs/*_avito.log`:
- `пазл: … вырез x=… (уверенность …), довели с ошибкой X px (перед отпусканием Y px), GeeTest ответил: …`. X near 0 and still `fail` → the found x or GeeTest's behavioural score, not the drag; X large again → the settle logic; X ≠ Y → the piece was still moving at release.
- «уверенность … , мало» (< 2.5) means the cutout was not really recognised; `logs/snapshots/*_пазл_фон.png` / `*_пазл_кусочек.png` hold that puzzle (run `app.captcha.find_gap` on them offline; never pass a live captcha).
- Still open: sparse pages (41–45 of 50 cards) — hypothesis is Avito serving fewer cards to flagged sessions.

On 2026-11-03 the macOS fork's CI (a slower machine) caught the X ≠ Y case for real: `Mouse.drag` settled the piece *before* each correction but released the slider right after the last one, while the piece was still travelling. Fixed in `RealtyWatch_Mac` (commit 53925c2): the drag settles once more when the corrections run out, and `net.box()` waits for a wheel scroll to stop before measuring an element, so clicks stop landing beside the link. The release half is now in `RealtyWatch_Win` too (d85708f, a `for … else` that calls `_settled` when the corrections run out): the slider test's lag assertion failed on this machine as well, [1.8, 1.6] against a 1.5 allowance, and passes after it — so «перед отпусканием Y» in the log can be trusted from now on. The `net.box()` half is in too (f68bf07, a `_still()` that waits for the element to stop and a public `Mouse.idle`): measured on the local mock, `box()` returned a rectangle a full wheel notch (100 px) stale in 1 of 8 runs under test timing and the click point held «Популярные запросы» instead of the link, 0 of 14 after — while production timing hid it on this machine (0 of 8), so only a slow or loaded machine shows it. `box()` is also ~2× faster in production timing now; the suite grew 137 s → 144 s.
On 2026-11-08 the CI flake was tracked down and fixed in `1539def` (ported to the fork after). All 3 of the 24 `mac.yml` reds (2 Nov twice, 6 Nov) were the same assertion, `max(lags) <= 1.5` with 2.2 / 1.7 / 1.8. `_settled` compared each reading with the previous one and read a move under 0.25 px as "the piece arrived" — but the page pulls the piece towards the handle a little with every frame it draws, so when frames are rare it creeps by fractions of a pixel with a long way still to go, and two near-equal readings mean "the page did not draw". Reproduced deterministically by replacing `requestAnimationFrame` with `setTimeout(follow, N)` in the mock (lag before release / aim error): 16 ms 0.2/0.6 px, 25 ms 0.9/0.6, 33 ms 3.4/**20** px (red 2 of 2, puzzle rejected), 100 ms 10/25. CI's 1.7–2.2 sits between 25 and 33 ms, i.e. the runner drew the page ~35–40 times a second under load average 7.65. Stillness is now judged over time (< 0.05 px in 0.35 s, budget 4 s), loosely while the target is far and strictly on the last reading, and an unsettled reading makes no correction at all. CPU load alone does **not** reproduce this on the user's 16-core Windows box (0 of 10 even pinned to 2 oversubscribed cores) — the frame clock is the lever.

**How to apply:** the mock's frame rate is now a knob — `self.site(frame=33)` in `tests/test_slider.py`, and `test_slow_page_is_not_mistaken_for_a_stopped_piece` guards the fix (red 2 of 2 with the old wait). To re-measure, the scratch harness `slider_loop.py` (`n=`, `frame=`, `cores=`, `load=`, `old`) prints every settle.
